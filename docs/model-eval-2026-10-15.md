# 로컬 모델 코딩 성능 비교 (2026-10-15)

Ornith, Tiel, Gemma 4 세 모델을 같은 llama.cpp, 컨텍스트 16k, 같은 플래그, 같은 러너로 측정했다.

## 결과

| | Ornith (Q4_K_M) | Tiel (Q4_K_XL) | Tiel+MTP (Q4_K_XL, draft-mtp) | Gemma 4 26B-A4B (Q3_K_M) |
|---|---|---|---|---|
| HumanEval / HumanEval+ (164, greedy) | 90.2% / 87.2% | 91.5% / 88.4% | 미채점* | **97.0% / 93.3%** |
| MBPP / MBPP+ (앞 100문제) | 87.0% / 80.0% | 89.0% / 78.0% | - | **94.0% / 84.0%** |
| 에이전트(polyglot 12문제) 1차 시도 통과 | 7 (58%) | 4 (33%) | **9 (75%)** | 5 (42%) |
| 에이전트 2차 시도(실패 로그 제공)까지 | 9 (75%) | **10 (83%)** | 9 (75%) | 9 (75%) |
| 답안당 평균 토큰 | 179 | **128** | **128** (동일 모델) | 263 |
| 생성 속도 (tok/s) | 41.8 | 39.0 | **56.4** | 37.7 |

\* MTP는 HumanEval 30문제로 속도만 측정했고 채점은 안 했다. 16k에서는 26/30문제가 출력 완전 동일(4문제는 greedy 수치 오차로 추정), 86k 실사용 설정에서는 30/30 완전 동일이었다.

에이전트(polyglot) 측정은 실제 `harnesside` 루프(도구, 컴팩션, 시스템 프롬프트 포함)로 풀게 했다. 문제는 34개 중 균등 추출한 12개이며, `forth`는 세 모델 모두 풀지 못했다.

- **속도는 Tiel+MTP가 가장 빠르다.** 16k에서 39.6→56.4 tok/s (1.42배). 실사용 설정(`-c 86016 -ngl 40 --n-cpu-moe 34`)에서도 36.5→53.4 tok/s (1.46배)로 이득이 유지됐다. MoE 오프로드 병목을 MTP가 상당 부분 상쇄했다. PolyStrata 엔진의 약 70 tok/s에는 못 미친다.
- **단, MTP는 VRAM을 약 800~900MB 더 쓴다.** 86k 측정 중 여유가 MTP 끔 1,254 MiB → 켬 386 MiB였다. 안전 여유(600 MiB)보다 얇아서, 교체 후 첫 기동 시 자동 재캘리브레이션이 `--n-cpu-moe`를 올릴 가능성이 있다. 그러면 실사용 속도는 측정치(53.4)보다 약간 낮아질 수 있다.
- **MTP는 1차 시도 성공률을 끌어올렸다.** Tiel 기준 4/12 (33%) → 9/12 (75%). 새로 1차 통과한 문제는 `bottle-song`, `grep`, `poker`, `react`, `transpose` 5개다. 2차까지는 10/12 → 9/12로 차이 없다.
- **단, 2문제는 퇴보했다.** `paasio`, `scale-generator`는 MTP 끔에서 2차에 통과했으나 MTP 켬 첫 측정에서는 1·2차 모두 실패했다. 재측정 결과 `scale-generator`는 1차 통과(노이즈였음), `paasio`는 2회 연속 실패(재현됨, 아래 재측정 항목).
- n=12라 단정은 금물이다. 1차 기준 McNemar: MTP켬 대 끔 p≈0.06(경계선), 대 Ornith p≈0.5(차이 없음). 2차 통과 집합은 MTP켬과 Ornith가 정확히 같다(같은 9문제).

## 재측정 (paasio, scale-generator — MTP 켬, 완료)

- `scale-generator`: 1차 통과 (337초, 도구 9회). 첫 실패는 노이즈였다.
- `paasio`: 1·2차 모두 실패로 재현됐다 (600+600초, 첫 측정과 동일). MTP 끔은 2차에 통과했고 Ornith는 둘 다 실패했다. `paasio`는 MTP 켬에서 2회 연속 실패라 재현성 있다.
- 정리: MTP로 풀 수 있는 문제는 10/12 (`forth`, `paasio` 제외). MTP 끔도 10/12 (`forth`, `transpose` 제외), Ornith는 9/12. 풀 수 있는 집합이 한 문제씩 다를 뿐 총량은 같다.

## 해석

- **함수 단위 코드 생성은 Gemma가 가장 높다.** HumanEval+에서 Gemma 대 Ornith 차이는 통계적으로 유의하다(정확 McNemar p=0.021, Gemma만 맞힌 문제 13개 대 Ornith만 맞힌 문제 3개). Gemma 대 Tiel은 경계선(p=0.096).
- **Tiel은 Ornith와 정확도 차이가 없다**(p=0.77). 모델 카드의 "SWE-bench-Live +4문제"는 재현되지 않았다. 확인된 차이는 답이 짧다는 것(Ornith보다 약 29% 적은 토큰).
- **에이전트로는 셋이 구분되지 않는다.** 12문제라 95% 신뢰구간이 매우 넓다(75%는 약 47~91%).
- **Gemma의 에이전트 성향**: 도구 호출이 적고(문제당 14회, 나머지 22~23회) 쉬운 문제도 느리다(1차 통과 문제 중앙값 316초, Ornith 146초). `paasio`는 두 번 모두 6분 안에 포기했다.
- **속도는 세 모델이 같다**(약 38~42 tok/s). MoE 오프로드가 병목이라 Gemma의 작은 Q3 파일도 이득이 없었다. PolyStrata 엔진의 약 70 tok/s는 이번 측정과 별개다.

## 객관적 수준

- HumanEval+ 87~93%는 EvalPlus 리더보드(2024년 스냅샷: GPT-4o 87.2%, o1-preview 89.0%, Qwen2.5-Coder-32B 87.2%)의 상위권과 비슷하거나 높다. 다만 이 벤치마크는 포화 상태라 변별력이 낮다.
- 에이전트는 쉬운 Python 문제 12개에서 피드백 포함 75~83%이고 어려운 문제(`forth`, `scale-generator` 등)는 실패했다. Aider 전체 리더보드(6개 언어 225문제)와 문제 구성이 달라 직접 비교할 수 없다. 벤더가 발표한 SWE-bench 값은 검증하지 못했다.

## 한계

- polyglot은 문제 12개, 1회 실행이라 차이를 판정하기엔 부족하다.
- 1·2차 시도는 Aider 방식과 다르다. 에이전트가 `run_shell`로 스스로 테스트를 돌릴 수 있었고, 2차에서는 실패 로그를 받았다.
- HumanEval+, MBPP+는 사고(thinking)를 끄고 greedy로, polyglot은 사고를 켠 하네스 설정으로 측정했다(Gemma 템플릿이 이 옵션을 무시했을 수 있음). polyglot 샘플링은 각 GGUF의 기본값.
- Gemma는 Q3, 나머지는 Q4 양자화라 양자화 차이가 섞여 있다.
- MBPP+는 378문제 중 100개만 측정했다.
- Tiel의 MTP 속도는 16k와 실사용 86k 설정에서 모두 측정했다(위 결과 절). 정확도 영향은 미채점이나, 86k 30문제는 출력이 완전히 같았다.
- MTP 에이전트 측정은 컨텍스트 16k에서 했다. 86k에서의 에이전트 성능은 미측정이다.

## 결론

- harnesside 기본 모델을 Tiel+MTP로 전환한다. 1차 시도 33%→75%(재측정 반영 시 `scale-generator` 포함), 생성 속도 1.42배(39.6→56.4 tok/s), 답 29% 짧음, 도구 호출 감소(259→232)가 근거다. 정확도는 Ornith와 차이가 없고(p=0.77), 2차까지 풀 수 있는 문제 수는 같다(10/12 vs 10/12 vs 9/12, 실패 집합만 한 문제씩 다름).
- `paasio` 퇴보는 재현됐으나 Ornith도 못 푸는 문제라 전환을 막을 이유는 아니다.
- 코드 생성 품질만 보면 Gemma 4가 뚜렷이 낫지만, 에이전트 성능은 같고 더 느리다.
- 확신을 높이려면 나머지 polyglot 22문제를 세 모델에 더 돌려야 한다(모델당 약 3.5시간).
- 원자료(문제별 결과와 로그)는 프로젝트에 저장하지 않았다.

## 위임 A/B (2026-10-17, X-8) — 표본 극소, 방향 확인용

같은 모델(Tiel+MTP, 90k)로 합성 과제 3개(여러 파일 이름 변경 / 옵션 추가 / 페이지네이션 버그)를 **조건당 1회**씩. A = "delegate 쓰지 말고 직접", B = "delegate 로 맡겨라". 통과 판정은 하네스 밖에서 `npm run check`.

| 과제 | A 통과 | A 시간 | A 로컬 모델 호출 / 도구 호출 | B 통과 | B 시간 | B 로컬 호출 / 도구 호출 |
|---|---|---|---|---|---|---|
| 이름 변경 | O | 104s | 9 / 14 | O | 97s | 6 / 5 |
| 옵션 추가 | O | 167s | 9 / 10 | O | 97s | 5 / 5 |
| 버그 수정 | O | 68s | 5 / 5 | O | 179s | 6 / 8 |
| 합계 | 3/3 | 339s | 23 / 29 | 3/3 | 373s | 17 / 18 |

- 읽을 수 있는 것: 둘 다 3/3 통과. B 는 로컬 모델 호출이 23→17 로 적었다. 시간은 과제에 따라 갈렸다(버그 수정은 B 가 느림 — 외부 에이전트 기동·검증 시간).
- **읽을 수 없는 것**: 컨텍스트 사용량·압축 횟수·VRAM 피크는 **미측정**(스트리밍 응답에 usage 가 없어 토큰이 0 으로 찍혔고, 세션 파일은 이 러너에서 저장되지 않았다). 과제가 작아 압축은 어느 쪽도 일어나지 않았다. 클라우드 비용도 미측정.
- 조건당 n=1 이므로 "위임이 낫다/나쁘다"는 결론을 내리지 않는다. 긴 과제·반복 측정이 필요하다.

### 위임 A/B 2차 (2026-10-17) — 컨텍스트·VRAM 계측 추가, 과제 4개 × 조건당 2회

러너가 `onContextUsage`(로컬 컨텍스트 최대 사용 토큰), 압축 횟수, `nvidia-smi` 3초 샘플링 VRAM 피크를 기록한다. 과제 4번(8개 모듈·약 1,600줄에 걸친 이름 변경)을 추가. 통과 판정은 하네스 밖 `npm run check`.

| 조건 | 실행 | 통과 | 합계 시간 | 로컬 모델 호출 | 도구 호출 | 컨텍스트 최대(평균 / 최댓값) | 압축 | VRAM 피크 |
|---|---|---|---|---|---|---|---|---|
| A 직접 | 8 | 8/8 | 1,254s | 99 | 113 | 5,279 / 7,584 | 0 | 7,663 MiB |
| B 위임 | 8 | 8/8 | 1,002s | 58 | 63 | 4,756 / 6,611 | 0 | 7,658 MiB |

- 읽을 수 있는 것: 통과율 동일(8/8). B 는 로컬 모델 호출 99→58, 도구 호출 113→63, 합계 시간 1,254→1,002s. 컨텍스트 최대 평균은 약 10% 낮았을 뿐이다(5,279→4,756).
- **컨텍스트 절감은 이 과제 크기에서는 의미 있게 관측되지 않았다.** 모든 실행이 90,112 중 7.6k 이하라 압축이 한 번도 일어나지 않았다. 위임의 컨텍스트 이득은 압축이 문제 되는 긴 작업에서 따져야 하며 여기서는 **미검증**.
- VRAM 피크는 서버가 상주해 있어 두 조건 모두 ≈7.6 GiB — 위임이 VRAM 을 바꾸지 않는다(로컬 모델은 한 개, 외부 에이전트는 클라우드).
- 과제별로 편차가 크다(예: 이름 변경 A 199s / 62s). 조건당 n=2 이므로 시간 차이는 잡음일 수 있다. 클라우드 `claude` 비용은 미측정.

### 위임 A/B 3차 (2026-10-17) — 큰 과제 + 하네스 컨텍스트 창 10,000 제한

16개 모듈·약 4,350줄에 걸친 이름 변경, 조건당 3회. 압축 압박을 만들려고 **하네스의 `contextWindowTokens` 만 10,000 으로 줄였다**(실서버는 90k) — 실제 긴 작업의 재현이 아니다.

| 조건 | 통과 | 시간(각 회) | 로컬 호출 합 | 컨텍스트 최대(각 회) | 압축 |
|---|---|---|---|---|---|
| A 직접 | 3/3 | 97 / 66 / 66s | 20 | 5,315 / 4,919 / 3,945 | 0 |
| B 위임 | 3/3 | 106 / 112 / 154s | 14 | 4,514 / 4,271 / 4,483 | 0 |

- **압축은 6회 모두 일어나지 않았다.** 로컬 모델이 전체 파일을 읽지 않고 grep/치환으로 처리했고, 도구 출력은 X-2 예산 게이트가 잘랐다. 즉 이름 변경류는 파일이 커도 컨텍스트를 키우지 않아, **이 과제로는 위임의 컨텍스트 이득을 관측할 수 없다.**
- 위임(B)의 시간은 이 과제에서 오히려 길었다(외부 에이전트 기동·검증 포함). 컨텍스트 최대는 약간 낮거나 비슷(평균 4,423 vs 4,726).
- 결론: "위임이 컨텍스트를 줄인다"는 **측정으로 확인되지 않았다.** 이득이 있다면 파일을 실제로 통째로 읽어야 하는 분석·리뷰형 작업일 텐데, 그 과제는 아직 측정하지 않았다.

### 위임 A/B 4차 (2026-10-17) — 읽어야 하는 탐색·수정 과제, 창 10,000 제한

16개 모듈·약 4,300줄 중 규칙이 다른 함수 1개(`helper11_33`, 부호 반대)를 **위치를 알려주지 않고** 찾아 고치게 했다. 조건당 3회, 하네스 `contextWindowTokens` 10,000 (인위적 제한).

| 회차 | A 직접: 시간 / 로컬 호출 / 압축 / 컨텍스트 최대 | B 위임: 시간 / 로컬 호출 / 압축 / 컨텍스트 최대 / 위임함 |
|---|---|---|
| 1 | 579s / 27 / 13 / 7,465 | 514s / 27 / 9 / 7,265 / O |
| 2 | 176s / 14 / 0 / 6,331 | 230s / 8 / 5 / 7,510 / O |
| 3 | 500s / 28 / 17 / 8,179 | 286s / 21 / 13 / 7,303 / **X (위임 안 함)** |
| 합 | 통과 3/3 · 1,255s · 69 · 압축 30 | 통과 3/3 · 1,030s · 56 · 압축 27 |

- 이 과제에서는 **처음으로 압축이 일어났다**(A 30회, B 27회). 이름 변경류(3차)와 달리 코드를 읽어야 하기 때문.
- 위임 조건에서도 **압축이 거의 줄지 않았다**(30→27). 컨텍스트 최대 평균은 사실상 같다(7,325 vs 7,359). 로컬 호출 69→56, 시간 1,255→1,030s 는 B 3회차가 위임을 하지 않고 직접 처리한 것이 섞여 있고, n=3 이라 잡음 범위일 수 있다.
- 위임했던 회차(1·2)에서도 로컬 모델이 8~27 번 호출하고 압축이 5~9회 났다 — 모델이 위임 전에 먼저 탐색하거나 위임 뒤 결과를 다시 확인했다고 추정되나 **로그로 확인하지는 않았다**.
- 결론: 위임이 컨텍스트 압박을 줄인다는 증거는 **여전히 없다.** 현재 구현에서는 로컬 모델이 위임 전후에 스스로 파일을 읽는 한 이득이 나지 않을 수 있다(원인 미확인).

### 위임 조건 도구 호출 추적 (2026-10-17) — 같은 4차 과제, 위임 조건만 3회, 호출 순서 기록
